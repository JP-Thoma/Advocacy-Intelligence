# Decision log

Status: D = decided, O = open. Every entry: decision, rationale, what would change it.

## Product

- **D1 Product:** HRW Recommendation Consistency Assistant. AI retrieves precedent and highlights differences; humans decide. *Why:* concrete task, no policy judgement by AI. Rejected: impact tracking, generic chat.
- **D2 Interaction:** manual invocation, two inputs: pasted recommendation text (primary) and uploaded report PDF (secondary, reuses the extractor). *Assumption, unvalidated:* HRW staff draft recommendations in some place we cannot see.
- **D3 Never paraphrase:** prior recommendations are always shown verbatim from source. Derived fields (normalised actor, action summary) are labelled model-generated.
- **D4 MVP cuts:** multiple document-type handling, reviewer feedback buttons, near-duplicate handling are deferred. *Caveat:* design records so grouping near-duplicates can be added later (repeated recommendations across years are the core signal).
- **D5 Corpus:** public HRW documents from the HRW website filtered for Lebanon. This is corpus scoping, NOT a retrieval filter. Retrieval must not hard-filter on geography.
- **D6 Must work or the POC is pointless:** reliable extraction of recommendations (verbatim, correctly bounded) and a comparison that does not invent differences.
- **D7 Matching:** semantic matches are enough (draft need not equal prior wording). Matches are always displayed as verbatim quoted spans. Primary matching dimensions: actor and issue; geography secondary. Each result shows which dimension matched.
- **D8 Corpus growth:** uploaded drafts are compared against the corpus but never auto-added. Only published reports may be added later.
- **D9 POC success question:** "Does this work with a corpus of ~10 previous reports?"
- **D10 System of record:** Blob Storage holds authoritative recommendation records (JSON); AI Search is a derived, rebuildable index. Cosmos DB deferred to the scale discussion.
- **D11 Normalisation is in scope:** actor and topic normalisation, using small controlled vocabularies built bottom-up from the corpus (not designed upfront). Raw strings are kept alongside normalised values.
- **D12 Trust signals:** (1) deterministic verbatim check, (2) link to exact source passage, (3) offline precision/recall on a hand-labelled set. No LLM self-reported confidence.
- **D13 Embedding:** enrich corpus recommendations (actor, topic, text) before embedding (option 2). Keep the verbatim text in a separate field. Whether the draft side is bare, enriched or both is decided by experiment (see build plan M6).
- **D14 Strength of language:** LLM-judged, but it must quote the operative phrase from both sides and code verifies the quotes. User's decision, over the proposal of a code lexicon; revisit if evaluation shows instability.
- **D15 Evaluation design:** leave-one-out on the newest report plus synthetic edited drafts with known differences.

- **D16 Metrics (delegated to assistant by user):** five metrics: verbatim match 100%; extraction recall >=90%; extraction precision >=85%; retrieval hit rate@5 >=90% of drafts; comparison faithfulness >=95%. Stop signal: recall <75% after iteration or hit rate <70%. Thresholds are initial and revisited after the gold set exists (small sample, wide uncertainty).
- **D17 Hosting (delegated):** review app on Azure Container Apps (scale to zero, Managed Identity). Ingestion is a local Python script writing to Blob for the POC, packaged to run later as a Container Apps job. Event-driven (queue + Functions/jobs) is the scale-up story. App Service is an acceptable alternative; not chosen.
- **D18 Index (delegated):** one recommendation-level AI Search index. Source context is stored in each record; no chunk index until evaluation shows a need.
- **D19 Embedding (delegated):** two vector fields per record (bare text, enriched text); both queried; the draft is parsed into editable fields shown to the user before comparison. Final variant chosen by experiment in M3.
- **D20 Full reports are PDF-only** (user observation), so PDF text extraction quality is the first thing to measure (M1). News releases and World Report chapters are HTML.

- **D21 UI stack:** FastAPI backend plus a thin frontend (plain HTML/JS or htmx served as static files; no React build chain). *Why:* the API is the contract and the UI is replaceable; user wants to learn FastAPI. *Cost:* second codebase; mitigated by keeping the frontend minimal. Supersedes the Streamlit assumption in D17 (hosting stays Container Apps).
- **D22 Key Vault:** not deployed in the POC (Managed Identity + RBAC means no secrets). Documented as a production control and as the key store for customer-managed keys in the Phase 8 confidential redesign.
- **D23 Raw data:** raw PDFs/HTML and records live in gitignored `data/` locally; a committed `data/sources.csv` manifest holds URL, title, date, type, retrieval date, hash. Blob becomes authoritative once ingestion uploads. Redistribution rights to be checked with Legal.

- **D24 Corpus (M0):** keep the 9 Lebanon PDFs already collected (2017-2024, mixed topics); do not add documents. *Consequence accepted:* only the Syrian refugee trio (2018, 2021, 2024) and possibly the two education reports offer natural precedent pairs, so the M0 criterion of 5 pairs may not be met. Mitigations: synthetic edited drafts carry more of the comparison evaluation; hit-rate@5 is reported with counts and an explicit small-sample caveat; the singleton reports act as distractors that test precision. Hold-out candidate: 202409 pushbacks report. *Revisit if* fewer than 3 genuine pairs are found.

- **D25 PDF text extraction (provisional):** pdfplumber (MIT) for M1, chosen by the user for quality over speed. *Evidence so far (M1 run, 9 reports):* body text and recommendation structure extract cleanly (actor headings, bullets, wrapped lines). Artefacts are deterministic and cleanable: `•(cid:3)` bullet glyphs, running headers/footers inside the text stream (including between pages of one recommendation list), footnote numbers fused to the preceding word (`planning.1`), end-of-line hyphenation. Open: 35 consecutive near-empty pages (144-178) in the 202302 LGBT report need a visual check. Document Intelligence not justified yet; decide after that check.

- **D26 Meaning of "verbatim":** option (b). A quote is verbatim relative to the original wording after a documented, deterministic, versioned cleaning pipeline (remove bullet-glyph junk, running headers/footers, footnote markers; join end-of-line hyphenation). Records store the source page and `cleaning_version`. Design rule to enforce by test: cleaning may only delete or join characters, never insert, reorder or substitute words, so cleaned text is always traceable to raw text. Raw page text is retained. Rationale (user): readability for researchers, plus the source link as a check.
- **D27 Scanned annexes out of scope:** the 202302 LGBT report's annex (PDF pp. 144-178: letters to governments and companies such as Meta) is low-quality scans, so no text is extracted (user finding). It contains no recommendations of the report itself, so it is excluded from the POC corpus scope and Document Intelligence is not adopted. It remains the documented production option for scanned material. Requirement: ingestion must report pages with no extractable text per document (coverage), never skip them silently.

- **D28 Draft input by file upload:** the draft box accepts .docx, .pptx, .pdf and .txt (max 5 MB). The server (`POST /api/extract`) returns candidate paragraphs and the user picks the recommendation to check; nothing is stored, and no LLM is used to find recommendations (that is phase 4). Office files are parsed with the standard library, PDFs with pdfplumber; scanned PDFs are rejected, not OCR'd. Uploads of confidential internal files are a phase 8 concern.
- **D29 Frontend vocabulary and content:** the UI says "topic" where the API dimension is `scope` (display label only, schema unchanged). "Matched on" and the "source context" box are removed from result cards as noise; `source_context` stays in the schema as possible comparison input. The principle statement moved to the footer and a short description sits under the header.
- **D30 Multi-recommendation review:** the input is a list of recommendations, not one. Results are clustered per input recommendation in a foldable section (all folded by default, opened if there is only one); the folded header is the overview (precedent count, difference count, difference types). Splitting is server-side (`POST /api/split`, deterministic: numbering must count 1, 2, 3 in order, plus bullets, blank lines and line breaks), so a model-assisted semantic split (user's stated ideal, phase 4) can replace it without UI changes. The browser calls `/api/check` once per recommendation (max 3 in parallel), so the contract is unchanged, results appear progressively, and each section has its own loading, error and retry. Corrections (wording, target actor, topic) are per recommendation; only fields the user changed are sent as overrides. No combined consistency score across recommendations (it would be a verdict).
- **D31 Result presentation:** precedents show only their retrieval rank ("Match 1", "Match 2", fixed by score and unaffected by re-sorting), with no percentage, bar or quality label, because a retrieval score is an ordering, not a measure of correctness (tier labels such as "Strong match" were tried and rejected by the user). Consequence: the UI cannot say that nothing relevant was found; a minimum-relevance cutoff belongs in retrieval and is to be calibrated against the gold set. The system's reading of each recommendation (actor, topic, geography) is one line ("Read as") that opens into the correction form, so results lead. The standing "humans decide" notice is a single muted line. Dark mode is dropped from the POC (user decision).

- **D28 Infrastructure as code:** Bicep. *Why:* Azure-only POC, no state file, Azure-native. Terraform considered for multi-cloud tooling, but its code is not portable across clouds (resources differ per provider), so that benefit is smaller than it looks. `azd` may be layered on later.
- **D29 Extraction model (user agreed to proposal):** start with a smaller model for batch extraction (speed irrelevant, verifier catches invented quotes); move up only if recall on the gold set is too low. Interactive path (draft parsing, comparison) decided separately because latency matters there.
- **D30 Region (provisional):** EU region preferred by the user (data-control instinct). Final choice by model availability and a deployment type that keeps processing in the EU (check regional/EU data-zone vs global). Public-only corpus, so not a legal gate yet; revisit with the Data Privacy Officer for confidential data.

- **D31 Azure subscription:** new personal subscription (personal Microsoft account, personal card), not an employer's tenant. *Why:* keeps any employer systems and data out of a proof of concept that uses public data only. *Consequences:* the user is tenant admin (can create app registrations; resolves part of O10); a reviewer would need a guest invite for hands-on access, so a live demo is the default. No employer or client data enters this subscription.

- **D32 Local-first demo:** the live demo runs from the user's own machine against Azure backing services (OpenAI, AI Search, Blob). App hosting (Container Apps, registry, App Insights, sign-in) is a stretch goal and otherwise documented, not built. *Why:* the demo is live, so hosting adds cost and attack surface without adding to the core evidence; resolves O10 (no public endpoint). Local app uses the developer identity via `az login` and RBAC. *Fallback:* a cached example from the real pipeline, clearly marked as cached, plus a recording. *Honesty rule:* say "designed for deployment, ran locally"; never claim production readiness.

Chat model is now a required Bicep parameter and is re-decided from fresh facts (other regions' DataZone quota, `gpt-5-mini` GlobalStandard, quota request). Original entry:  `gpt-4o-mini` 2024-07-18, deployment type regional Standard in Sweden Central, for both extraction and draft comparison. *Why:* quota check showed `gpt-5-mini` only as GlobalStandard (DataZoneStandard limit 0), which would break the "processing stays in the EU" statement; regional Standard gives positive quota (200) and the cleanest residency story. *Risks:* older model, check retirement date; unmeasured extraction quality. *Revisit at M5:* compare against `gpt-5-mini` (Global, public documents only) on the gold set. Option E (split by data sensitivity: public ingestion may use Global, user drafts EU-bound) is the documented alternative.
- **D34 Embedding model:** `text-embedding-3-large`, regional Standard (quota 350; DataZoneStandard limit was 0). Whether large beats `3-small` for this domain is untested; compare in M6 on the leave-one-out set.
- **D35 Foundation settings:** deployments named by role (`chat`, `embedding`) so models are swappable; capacity 30 (chat) and 20 (embedding), far below quota, as the spend brake; keyless by design (Storage shared keys off, Azure OpenAI local auth off, roles for the developer identity). Public network access stays on for the POC; private endpoints belong to the Phase 8 redesign. *Finding:* the free-trial subscription had non-zero model quota, contradicting community reports of zero, so no upgrade to pay-as-you-go was needed and the spending cap remains.

- **D36 Chat model (CONFIRMED by the user: "gpt-4o processed in Europe"; replaces D33):** `gpt-4o` 2024-11-20, regional Standard, Sweden Central, capacity 10. *Evidence (finder script, after excluding fine-tune quota rows):* no DataZoneStandard chat model has quota in Sweden Central, France Central or Germany West Central. Real options were `gpt-4o` Standard (Sweden Central only, quota 50, deprecates 2027-04-14), `gpt-4.1-mini` GlobalStandard (quota 200, 2027-04-14), `gpt-5-mini` GlobalStandard (quota 500, 2027-02-09). Chosen because it keeps all processing regional (Sweden Central), matching the earlier residency intent. *Trade-offs:* older and likely several times more expensive per token than a mini model (verify on the pricing page), so capacity is lowered from 30 to 10 to cap worst-case spend; deprecation is per deployment type, so check `skus[].deprecationDate`, not the model-level date. *Revisit at M5:* compare against `gpt-4.1-mini` / `gpt-5-mini` (Global, public documents only) on the gold set.

- **D37 Comparison deferred for the first release (user decision):** the demo delivers "find precedent" for real; LLM comparison (capabilities 2 and 3) is not built. *Why:* a fixed time budget of about 13 hours for the first release; comparison is also where hallucination risk concentrates. *Rules that follow:* the mock `differences` in the fixture must never be shown beside real results; the positioning is "scoped to the highest-value, lowest-risk capability; comparison is next, with quote verification (D14)". Results may show deterministic facts only (date, document, actor as written, matched dimensions). Budget raised for AI Search Basic (user agreed; suggested 100). Details in `docs/delivery-plan.md`.

- **D38 Ingestion design (M4, user decisions):** (1) *Scope:* the extractor reads only the recommendations section, found by heading, not the whole report. The user's reason was cost; the stronger reasons are precision (body text contains imperatives that are not HRW recommendations) and provenance ("under HRW's Recommendations heading" is checkable). Cost is minor (the trio is about 150k tokens). *Risk and rule:* a report where no section is found is a loud coverage failure, never an empty result; if recall on the gold report is low, fall back to reading every page. Open: 202303 has three recommendation-heading pages (probably summary plus full list), check for duplicates. (2) *Quotes by ID, not by model text:* code cleans and segments the section into numbered units (actor heading, then bullets); the model returns only unit IDs and metadata and never writes the quote, so wording is verbatim by construction. Rejected: the model returning text that code then substring-checks (a quietly "fixed" quote is lost recall). The substring check stays as a verifier because it guards our own cleaning and joining, not the model. Trade-off: an unusual layout needs a segmentation rule, and a segmentation error is consistent, so it is surfaced by the coverage report and gold check. (3) *Cleaner (clean-v1):* deletes bullet glyphs, running headers and footers, fused footnote digits; joins hyphenated breaks only before a lowercase line; unwraps lines. Bullet status is kept as structure (`Paragraph.kind`), not text. Delete-only invariant (D26) is tested on synthetic and real pages. *Known limits:* a real hyphen before a lowercase word is joined wrongly (unmeasured); a wrapped two-line actor heading is not modelled.
- **D39 Azure content filter blocks some recommendation text (finding; user chose option A):** the first real run over the trio (105 units) labelled 101; 4 units (201804 u001, u002, u014; 202409 u015) were rejected by Azure OpenAI's default content filter (`hate`, severity medium, on the prompt). They are recommendations that tell authorities to stop discriminating by nationality or religion, so the filter reacts to the subject, not the intent. *Decision:* accept and label honestly. Those records keep their verbatim quote, actor and provenance; only `action_requested` and `topic` are empty, the error is recorded as `content_filter (Azure policy)`, the coverage report shows 101/105, and the UI must say "labels unavailable" for them, never invent them. Content-filter errors are not retried (deterministic). *Rejected:* rewording the text to pass the filter (breaks the verbatim guarantee and evades a control without authorisation). *Production path:* request modified content filtering for this resource and re-run labelling; do not assume approval. *Why it matters:* safety filters are a real constraint for human-rights content, and the pipeline degrades per unit instead of failing or dropping records. *Other M4 facts:* labelling is one call per unit so the model never handles IDs (D38); about 30k input and 3.5k output tokens for the whole trio; one label added a topic not in the text ("housing rights"), a single data point for M5, not a measured rate.
- **D40 Search index design (drafted while the user labelled; not yet deployed or tested live):** one index `recommendations-v1`, one vector field (3072 dims, HNSW, cosine), keyword fields analysed with `en.microsoft`, no semantic ranker. *Why:* matches the first-release scope (one enriched vector, hybrid). Vectors are computed in our code, not by an index-side vectorizer, so the same embedding path serves ingestion and the draft query, and the cosine fallback (plan decision gate) needs no Search service. HNSW is not needed for ~100 vectors (an exact scan would do); it is kept as the scale-relevant choice and tuned (efSearch 500) to behave near-exactly. `document_id` is filterable so a held-out report can be excluded from its own evaluation. The definition is pure data (`indexing/schema.py`), unit-tested in CI; SDK calls live in `indexing/service.py` and are untested until the service exists. The index is derived and rebuildable from Blob records (D10). The Search resource is behind `deploySearch` (default false) in `infra/main.bicep`. *Open:* what text is embedded (user to decide: bare quote vs actor + quote + labels); 4 unlabelled records (D39) must still index.
- **D41 Gold check result and embedding text (user decisions):** (1) *Extraction gold check, 202409 only:* the user labelled all 33 recommendations from the PDF without seeing the system output; the extractor found 33/33 with 0 extra, identical text (exact, including punctuation), identical pages and actor headings, and the one bullet crossing a page break was joined correctly. *Caveats to state whenever this result is reported:* one report, 33 items, the cleanest layout of the trio; the other two reports were checked only by an independent bullet-glyph count (29/29, 43/43), not by a hand-labelled gold file; the metric covers the recommendations section only. The user's note that the executive summary repeats the recommendations in summarised form supports D38 (read the section only; the summary is not a second set of recommendations) for this report. No precedent links were labelled yet. (2) *Embedded text = actor heading + quote + the model's labels (action_requested, topic), user decision.* Risks to manage: the 4 unlabelled records (D39) get a shorter text (missing lines are omitted, not invented); the vector now depends on model-generated labels (one label added a topic not in the text); a user draft has no labels, so the document side is richer than the query side. Mitigation: the draft is embedded as its text plus the actor if the user gives one (the UI already has that field), with no model labels added at query time; whether this asymmetry hurts is checked by the held-out test (202409 recommendations as drafts), not assumed. Embedding A/B (bare vs enriched) stays cut from the first-release scope.
- **D42 Real retrieval wired with a cosine retriever (first-release step 1); Azure sign-in finding:** 105 records embedded (actor + quote + labels, `embed-text-v1`) into a local `data/index/vectors.json`; `/api/check` returns real precedents when `ADVOCACY_RETRIEVAL=azure-cosine`, otherwise the fixture; in real mode `differences` is empty, `comparison_performed=false` (new contract field) so the UI says "Wording not compared yet" instead of "No differences noted", and any setup or Azure failure is a 503, never a silent fall back to the mock. *First held-out look (202409 recommendations as drafts, 202409 hidden, 33 drafts, top 3):* clear repeats rank first with high cosine (for example 2024 "Rescind the May 2019 Higher Defense Council's decision..." matches the 2021 wording at 0.92; "Allow UNHCR to resume registering..." at 0.93), while recommendations with no precedent in the corpus (the Cyprus ones) still return neighbours at about 0.6. *Weaknesses seen, unmeasured:* retrieval always returns something (a cutoff needs labelled pairs, D31); a few generic 2018 eviction recommendations recur as neighbours of unrelated drafts; the check lists results for human judgement and is not a score. *Sign-in finding:* `az login --use-device-code` failed with AADSTS530035 ("blocked by security defaults") for the personal account and for a new directory user alike; Microsoft's documentation says security defaults block the device-code flow, so the browser sign-in (`az login` with the sign-in URL opened in an incognito window; the CLI receives the result on localhost) is the working route on the work laptop. Do not switch security defaults off. A demo user created in the personal directory is not needed and is to be deleted with the resource group.
- **D43 Relevance threshold (user decision, design changed by evidence):** results whose similarity to the draft is below 0.42 are hidden, so clearly unrelated text returns no results and the UI says so ("No sufficiently similar prior recommendation was found among the indexed reports. This does not mean the topic has never been addressed."), with a count of hidden weaker candidates. *Why not a plain cutoff on the ranking score:* the embedded text includes the actor line (D41), which adds about 0.3 to every score; with an actor typed in, off-topic text scored 0.53 to 0.62, inside the real range (0.61 to 0.93 with actor). *Design:* each query embeds the draft twice in one call, with the actor for ranking and without it for the cutoff, and the cutoff compares the no-actor embedding with the same stored vectors, so the actor field cannot move it. *Calibration (44 texts, `evaluation/threshold_check.py`, re-runnable):* 33 real held-out drafts scored 0.50 to 0.86 (all pass); 6 synthetic off-topic sentences 0.19 to 0.34 (none pass); 5 synthetic rights-related sentences outside the corpus 0.32 to 0.57 (3 pass, expected). 0.42 sits between 0.34 and 0.50. *What it claims:* it removes clearly unrelated text. It does not decide whether a true precedent exists (recommendations with no precedent, such as the Cyprus ones, still score about 0.5 to 0.64), and rights-related text with weak overlap still returns weak neighbours. The value is configurable (`ADVOCACY_MIN_RELEVANCE`) and must be re-calibrated after any change of embedding model, embedded text or corpus. A calibrated hit rate still needs labelled precedent pairs.
- **D44 Hosting deferred (user decision):** no deployed app for now; runs locally (D32 stands). *Findings that make a later deployment a planned task and not a quick one:* none of the resource providers for hosting is registered (Microsoft.App, ContainerRegistry, OperationalInsights, Web), the container-apps CLI extension is missing, there is no local Docker (cloud image builds can be restricted on new subscriptions, unverified), the app has no sign-in so a public link needs at least an access code, and the records and vectors would have to be read from Blob (managed identity) so the image holds no HRW text. Redistribution rights for the displayed HRW wording (D23) should be checked before any public endpoint. *If hosting is picked up later:* Container Apps or App Service, managed identity with the same roles, access code or Entra sign-in, records and vectors loaded from Blob with a local fallback, a spend limit, and deletion afterwards.
